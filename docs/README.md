### Уточнение цели: один успешный ответ

После отчёта о wrong владелец явно возобновил отправки с целью получить **одно
подтверждённое правильное решение**, сохраняя один выбранный курс/шаг.
Для этого добавлен отдельный `--retry-wrong`; прежняя отправка не стирается.
Режим требует точные --course-id/--step-id и --canary, читает финальный wrong,
сверяет точные ID, владельца attempt, ответ и состав её истории. Pending,
изменившаяся история или неразрешённый POST запрещают новую попытку.
Обычный перезапуск по-прежнему не обходит attempted_today.

Для нового запуска создаётся/получается attempt через штатный API. Модель получает
подтверждённый прошлый verdict и выбранные тогда варианты по их текстам, чтобы
перестановка вариантов в новой attempt не сместила feedback. Требуются
boolean-массив и краткое обоснование; в Stepik уходит только проверенный reply.
Повтор прежнего отклонённого набора вариантов блокируется до POST.
Прежние jobs архивируются в приватном job_history, новый job содержит retry_of
и счётчик. Максимум три таких повтора на шаг, один POST за запуск; после
подтверждённого success дальнейшие canary той же модели заблокированы.
Бюджет и журнал переживают сбой; неоднозначный POST допускает только reconcile.
Версия prompt для binding обновлена до stepik-json-v7.

`--lesson-context` дополнительно читает только предшествующие текстовые блоки
этого же урока с проверкой ID lesson/steps. Полные предложения ранжируются по
словам вопроса и вариантов; сохраняется заголовок источника, чтобы не потерять
принадлежность определения. Условия других оцениваемых заданий не используются.
В prompt помещаются только целые выдержки в прежний byte-budget 1504; слишком
длинные предложения пропускаются. Если ни одна не помещается, отправки нет.
В отчёт попадают только source step IDs и число выдержек, без текста.
Все прежние wrong перепроверяются и блокируются по смысловому набору вариантов;
для экономии контекста модель получает их массивами в порядке **текущего** dataset.
Краткое обоснование ограничено 240 символами и не отправляется в Stepik.
Для утверждений вроде «оба типа относятся…» категория связывается с названиями
определённых в том же учебном блоке типов. Это эвристика извлечения, не доказательство
правильности: живые пробы Qwen всё ещё wrong, несмотря на исправленный контекст.

```bash
.venv/bin/python bot.py --canary --course-id 171826 --step-id 4613252 --retry-wrong --lesson-context --max-candidates 1 --max-submissions 1 --max-runtime 900
```

101 тест проверяет исходный аудит/восстановление и новый режим: без явного флага
повтора нет, изменившийся verdict/history и исчерпанный бюджет блокируют запись,
прежняя посылка сохраняется, ответ не повторяется при перестановке options.
Отдельно проверены ID урока, чтение только предшествующей теории, упаковка целых
предложений в контекст, source IDs в метриках и запрет любого прежнего wrong.
Trial и ежедневный таймер этим режимом не включаются.

Если reviewed-генерация отказалась/не прошла локальную проверку **до POST**, есть
явный `--resume-review` вместе с --retry-wrong и тем же scope. Он сверяет связь
retry_of с архивом, отсутствие sent_at/submission_id/reply и неизменную baseline
истории текущей attempt; создаётся только GET существующей attempt, новой attempt
не создаёт. До GET резервируется отдельный review_retries (не более двух).
При неопределённой отправке этот путь закрыт; используется только reconcile.
В тестах подтверждено переиспользование attempt без потери истории и блокировка
любых признаков POST/исчерпанного бюджета. Никакие счётчики/старые jobs не стираются.

## Архитектура и конфигурация

`systemd timer → bot.py → Stepik HTTPS API + локальный шлюз → llama.cpp → GGUF`.

| Компонент | Значение |
| --- | --- |
| LLM base URL бота | `http://127.0.0.1:18085/v1` |
| Генерация | `POST /v1/chat/completions`, SSE, JSON response_format |
| Авторизация | отдельный Bearer-ключ `stepik`, только на Pi |
| Модель API | `raspberry-llm` |
| Веса | Qwen3-4B-Instruct-2507 Q4_K_M |
| Контекст / выход | 2048 суммарно / до 384 токенов |
| Существующий внешний API | `https://skin-cancer-ai.ru/v1` |
| Существующий чат | `https://skin-cancer-ai.ru/llm/` |

Backend остаётся `127.0.0.1:11434`; бот пользуется защищённым шлюзом.
Клиент запрещает удалённый endpoint, redirect и proxy окружения.
Preflight проверяет `/v1/models`, runtime-контекст через `/llm/props` и SHA256
фактически загруженного GGUF из процесса `raspberry-llm`. Хеш кэшируется по
пути/размеру/mtime/ctime. Пробы привязаны к весам, контексту, лимиту ответа и
версии prompt; одного совпадения API alias недостаточно.

Существующие параметры модели: 3 потока, CPUQuota 250%, Nice 10, один слот.
При занятом слоте бот обрабатывает `429 Retry-After`, ждёт до 120 с суммарно.
После исчерпания бюджета ответ не отправляется в Stepik, причина попадает в отчёт.
HTTP read timeout и deadline потока — 650 с, timeout всего запроса шлюза — 600 с.
Обрыв SSE, `length`, отсутствие `[DONE]` и невалидный JSON запрещают отправку.

HTML условия очищается с сохранением переводов строк; лишние editor metadata и
шаблоны других языков не отправляются. Сумма UTF-8 байтов инструкции и задачи
ограничена `2048 - max_tokens - 160` (1504 при 384). Это консервативная граница
для byte-level tokenizer, а не замер токенов: часть длинных задач пропускается
как `context_too_large`. Контекст и параметры llama.cpp не увеличивались.

## Ввод OAuth: действие владельца

В своём браузере войти в Stepik и создать приложение на
[странице OAuth](https://stepik.org/oauth2/applications/): Client type
**Confidential**, grant type **Client credentials**, под нужным аккаунтом.
Пароль Stepik не нужен. Грант и `read write` документированы в
[официальном API](https://github.com/StepicOrg/Stepik-API#oauth-2).

В обычном собственном терминале, не в терминале агента с записью ввода:

```bash
ssh -t raspberry 'python3 /home/admin/projects/stepik-daily-bot/configure.py'
```

Client ID и secret вводятся скрыто. Числовой user ID взять из URL своего профиля.
Скрипт создаёт приватный `stepik.env`, существующий файл не затирает.
Ключи в чат не присылать. Последующие изменения — локальным редактором на Pi.

### Возобновляемый checkpoint

`~/.local/state/stepik-daily-bot/audit.sqlite3` хранится вне Git с правами 600,
каталог 700, SQLite WAL + synchronous=FULL. В базе только ID, статусы, хеши
метаданных, результаты проверок и курсоры — без токенов, условий и ответов.
Проверенная страница истории записывается одной транзакцией вместе с курсором,
раздел — только после успешного чтения всех его подходящих шагов.
При чтении истории до пяти страниц объединяются для проверки владельцев
попыток пакетами по максимум 100 ID (поддержка подтверждена реальным API;
обычно один GET при 20 строках на странице).
Каждая проверенная страница всё равно коммитится отдельно. Другие ресурсы и
пишущий клиент используют прежние небольшие пакеты по 20 ID.
Повторить ту же команду — штатное продолжение после SIGINT/SIGTERM/сбоя.
Перед первым GET новый запуск атомарно заменяет latest-dry-run.json на неполный
маркер. Даже SIGKILL без finally не оставляет старый успешный отчёт разрешением
для записи. Пишущему запуску нужен полный отчёт не старше 24 часов.
Прерванный текущий раздел перепроверяется; ранее завершённые разделы используют
сохранённые результаты с проверкой актуальности.

Для явно выбранного курса доступен отдельный полный аудит его доступных разделов:

```bash
.venv/bin/python bot.py --dry-run --course-id 171826 --max-candidates 100000 --max-steps 100000
```

`--course-id` можно повторять. Такой аудит читает свежую полную историю каждого
подходящего шага выбранных курсов, не повторяет постороннюю историю аккаунта и
сохраняет отдельный audit-courses-HASH.sqlite3. Отчёт содержит audit_scope;
inventory_complete означает полноту только этого scope, account_inventory_complete
остаётся false. Scoped отчёт разрешает canary/trial только с явно совпадающим
--course-id и только для перечисленных в отчёте кандидатов. Ежедневный --submit
им не разрешается. Перед POST всё равно читаются свежие progress/history.

Checkpoint привязан к аккаунту, версии и политике аудита, max_steps,
max_candidates и target. Несовпадение не стирает базу: запуск останавливается.
Для намеренной смены параметров есть `--restart-audit`; он сбрасывает читающие
курсоры своего аккаунта, сохраняя факт ранее проверенных correct. Для другого
аккаунта нужен другой STATE_DIR; переиспользовать журнал прежнего аккаунта нельзя.
max_runtime можно менять без сброса checkpoint.

После перерыва проверяются первая и последняя сохранённые страницы истории.
Если сместилась пагинация/изменились границы, история и кэш разделов сбрасываются
и читаются заново; неоднозначный результат не разрешает отправку. При неизменной
истории нет повторного прохода всех 1638 страниц и повторного чтения attempts.
Новые курсы/разделы обнаруживаются по свежему списку. Структура units/lessons
и метаданные steps сверяются пакетно даже для сохранённых разделов: на каскадное
обновление родительских timestamps предположений нет. Переиспользуются только
неизменные исключения; кандидаты, их progress и история своего шага проверяются
свежими GET с проверкой владельца/step ID попыток. Отсутствие записи в старом
кэше никогда не является единственным доказательством новизны.

Stepik API не предоставляет атомарный snapshot всего аккаунта. Итоги относятся
к интервалу обхода; перед отправкой выбранный шаг проверяется снова. Изменение
вердикта внутри старой истории, не меняющее граничные страницы, ловится свежей
историей кандидата. Подтверждённое прежнее correct всегда исключает повторный шаг.

`expected_exclusion_reasons` отделяет ожидаемые исключения (exam, закрытые
разделы/units, подтверждённые HTTP 403/404 недоступных объектов, неподдерживаемые
типы и ограничения) от `read_errors` / `read_error_reasons`.
Неизвестный progress, неверная схема/дата, transport/5xx/429 и прочие
необработанные ошибки не маскируются под закрытый раздел.
`handled_api_errors` — ошибки пакетного GET, после которых отдельные GET
успешно проверили объекты; они не считаются необработанными.
`inventory_complete=true` только после обхода всех доступных подходящих разделов
без необработанных ошибок и без остановки по лимиту/прерыванию. Нормальные
исключения сами по себе не делают аудит неполным. Ошибочные разделы при
следующем запуске читаются заново. Количество исключений в отчёте может относиться
к разным единицам: например exam — к разделу, unsupported_type — к шагу.

Читающий API-клиент технически отвергает любой POST к ресурсам Stepik.
OAuth token exchange остаётся отдельным POST. Для canary создаётся свежий
пишущий клиент. Полный балл дополнительно подтверждается повторной идентичностью
аккаунта и чтением своей attempt с точными ID аккаунта/шага.

Реальный API проверен: lessons, steps, progresses и attempts поддерживают
пакетный GET по `ids[]`. Уроки и прогресс читаются пакетами внутри раздела.
Полная собственная история correct читается один раз на аудит с пагинацией;
владельцы и step ID сверяются через соответствующие attempts. Несовпадение
владельца/схемы останавливает аудит. Реальный `status=correct` возвращает также
legacy `settled`: статус проверяется локально; неизвестные/pending шаги
исключаются с причиной `prior_unknown_or_pending_verdict`, не засчитываются
как correct. Wrong/partially_correct не превращаются в прежние полные решения.
В пишущих запусках индекс не используется:
нужен новый клиент и свежие GET перед отправкой. Ход обхода виден в
`reports/inventory-progress.json`. Прерванный аудит помечается incomplete,
не открывает режим отправки и не выдаётся за полный запас задач.

В отчёте: `course_list`, `per_course.types/reasons/candidates`, `api_samples`,
`inventory_complete`, `traversal_skips`, `stop_reason`. Кандидат имеет явный
`progress=false` и не имеет прежних correct в полной истории. `candidates // 26`
— верхняя граница дней только при 100% успехе и пригодности свежих dataset.
При неполном обходе весь запас неизвестен. Ошибка OAuth не означает ноль задач.

`api_samples` читает существующие attempts/submissions максимум у 20 шагов
(до трёх образцов каждого поддержанного типа, включая уже решённые):
сохраняются типы полей, форма dataset/reply и известный статус без значений ответа.
Пустая история не подтверждает формат свежей попытки: он проверяется в пробе.
Форматы сверены с официальными
[SubmissionUtility](https://github.com/StepicOrg/SubmissionUtility/blob/master/submitter.py)
и [Android-моделями](https://github.com/StepicOrg/stepik-android/tree/master/model/src/main/java/org/stepik/android/model).
Это публичные контракты, не захват API вашего аккаунта.

После изучения полного отчёта запаса — одна проба:

```bash
.venv/bin/python bot.py --canary
.venv/bin/python bot.py --report
```

Для одной выбранной задачи после завершённого аудита курса:

```bash
.venv/bin/python bot.py --canary --course-id 171826 --step-id 4613252 --max-candidates 1 --max-submissions 1 --max-runtime 900
```

`--step-id` разрешён только в canary и должен присутствовать среди кандидатов
свежего завершённого аудита. Остальные шаги исключаются до создания попыток.
Если единственная генерация была отклонена **до отправки** как invalid_choices,
явный `--resume-generation` с теми же --course-id/--step-id допускает один повтор
генерации. Он GET-ом читает прежнюю attempt и сверяет её владельца и шаг;
новой attempt не создаёт. Наличие sent_at/submission_id/reply, прежней посылки,
другой причины отказа или использованного повтора запрещает этот режим.
Повтор резервируется в журнале до GET/генерации и переживает сбой.
Это не повтор POST: сомнительная отправка допускает только reconcile;
wrong/неоднозначный вердикт не компенсируется следующей задачей.

Максимум один POST ответа за вызов, даже если ответ wrong. Прогресс, история и
граница UTC перепроверяются после модели и непосредственно перед POST.
Успешная canary той же модели повторно не отправляется. Открыть
`https://stepik.org/step/STEP_ID`, сверить полное принятие и submission ID из state.
Затем зафиксировать свою визуальную проверку и провести малую серию:

```bash
.venv/bin/python bot.py --approve-canary
.venv/bin/python bot.py --trial
.venv/bin/python bot.py --report
```

`--trial` требует успешную canary и допускает до трёх POST за запуск.
Для ежедневного режима нужны три разных полностью принятых новых шага в trial,
та же модель/аккаунт и ручная проверка canary. Wrong, pending и skip не открывают
этот режим. Повторные осознанные запуски trial сохраняют дневные лимиты.
Правильные пробные решения входят в дневные 26, не идут сверх цели.

## Засчитывание и восстановление

Только новый уникальный шаг, своя посылка/попытка, `correct`, `score=1`, passed
progress и непротиворечивое серверное время с TZ. Wrong, partially_correct,
correct с неполным score, прежние решения и pending не засчитываются.
День — UTC-дата серверной посылки, а не запуска процесса.

Поддержаны choice, number, string, sorting, matching, math, Python 3 code при
проверенном dataset. Число строкой, выбор boolean-массивом нужной длины и
кардинальности, перестановки с нуля, Python language точно из шаблона.
Код на Pi не выполняется; ast проверяет только синтаксис, правильность — Stepik.
Экзамены, review, visual/внешние материалы, неизвестные типы, недоступные разделы
и шаги с ограничениями отправок пропускаются с указанной причиной.

`flock` исключает два экземпляра. Атомарная запись + fsync сохраняют журнал перед
POST. Потерянный ответ на POST не повторяется: `sending` блокирует дальнейшие
отправки до сверки через GET, с поддержкой прямого и wrapped reply.
Пустой ответ API после timeout не доказывает, что поздняя запись не появится.

```bash
.venv/bin/python bot.py --reconcile
.venv/bin/python bot.py --report
```

Не удалять state для снятия неоднозначности. Состояние другого аккаунта и
повреждённый JSON останавливают работу. Лимиты по умолчанию: 104 кандидата/попытки
в UTC-день, один шаг не более раза за день, до 104 POST за полный запуск, цель 26
подтверждений. Canary/trial имеют более строгие лимиты. Другой клиент или ручное
решение того же шага одновременно создают API-гонку: во время пробы так не делать.

Коды выхода: `0` — завершён полный аудит/режим или достигнута цель, `2` — недобор/неудачная проба,
`3` — неразрешённая отправка или блокировка Stepik, `1` — ошибка, `130` — остановка.
Для dry-run код `3` также означает сохранённый неполный аудит (например runtime_limit).
Отчёт: actual accepted, shortfall, причины, время на задачу, LLM usage/timings,
ID принятых шагов и неразрешённые посылки. `--report` пересчитывает счётчик
текущего UTC-дня: вчерашние 26 не выдаются за сегодняшний результат.

## systemd и эксплуатация

`.venv` создан через `python3 -m venv --system-site-packages`; используется
установленный requests. Тяжёлых служб/контейнеров нет, VPN и сайты не менялись.
Установщик без флага устанавливает/проверяет units и оставляет таймер выключенным:

```bash
bash scripts/install-systemd.sh
systemctl is-enabled stepik-daily-bot.timer
systemctl list-timers --all stepik-daily-bot.timer
systemd-analyze calendar '*-*-* 05:00:00 UTC'
systemd-analyze verify /etc/systemd/system/stepik-daily-bot.service /etc/systemd/system/stepik-daily-bot.timer
```

После всех живых проверок включить:

```bash
bash scripts/install-systemd.sh --enable
```

Установщик и `--submit` проверяют trial/canary. Без OAuth-файла systemd пропускает
запуск. `Persistent=true` догоняет пропущенный запуск после включения/загрузки.
Расписание 05:00 UTC / 08:00 Москвы; максимум 11 часов работы бота, TimeoutStartSec
12 часов. Остановка новых попыток/ответов за 20 минут до 00:00 UTC.
Restart on failure через 15 минут, максимум 3 запуска/час. Обычный недобор (exit 2)
не вызывает restart. Сначала восстановление журнала, потом новые задачи.

```bash
systemctl status stepik-daily-bot.service stepik-daily-bot.timer --no-pager
sudo journalctl -u stepik-daily-bot.service -n 60 --no-pager
systemctl status raspberry-llm raspberry-llm-gateway --no-pager
free -h
vcgencmd measure_temp
vcgencmd get_throttled
sudo systemctl disable --now stepik-daily-bot.timer
sudo systemctl stop stepik-daily-bot.service
```

Остановка может оставить sending: следующий запуск делает reconcile. Полный reboot
Pi не выполнен; перезапуск отдельных LLM-служб не равен проверке загрузки устройства.
Исходный ZIP сохранён. `python3 scripts/package.py` собирает архив по allowlist
без конфигурации, ключей, state, venv и журналов.
