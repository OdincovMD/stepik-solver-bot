## Архитектура и конфигурация

`systemd timer → bot.py → Stepik HTTPS API + локальный шлюз → llama.cpp → GGUF`.

| Компонент | Значение |
| --- | --- |
| LLM base URL бота | `http://127.0.0.1:18085/v1` |
| Генерация | `POST /v1/chat/completions`, SSE, JSON response_format |
| Авторизация | отдельный Bearer-ключ `stepik`, только на Pi |
| Модель API | `raspberry-llm` |
| Веса | Qwen3-4B-Instruct-2507 Q4_K_M |
| Контекст / выход | 2048 суммарно / до 384 токенов |
| Существующий внешний API | `https://skin-cancer-ai.ru/v1` |
| Существующий чат | `https://skin-cancer-ai.ru/llm/` |

Backend остаётся `127.0.0.1:11434`; бот пользуется защищённым шлюзом.
Клиент запрещает удалённый endpoint, redirect и proxy окружения.
Preflight проверяет `/v1/models`, runtime-контекст через `/llm/props` и SHA256
фактически загруженного GGUF из процесса `raspberry-llm`. Хеш кэшируется по
пути/размеру/mtime/ctime. Пробы привязаны к весам, контексту, лимиту ответа и
версии prompt; одного совпадения API alias недостаточно.

Существующие параметры модели: 3 потока, CPUQuota 250%, Nice 10, один слот.
При занятом слоте бот обрабатывает `429 Retry-After`, ждёт до 120 с суммарно.
После исчерпания бюджета ответ не отправляется в Stepik, причина попадает в отчёт.
HTTP read timeout и deadline потока — 650 с, timeout всего запроса шлюза — 600 с.
Обрыв SSE, `length`, отсутствие `[DONE]` и невалидный JSON запрещают отправку.

HTML условия очищается с сохранением переводов строк; лишние editor metadata и
шаблоны других языков не отправляются. Сумма UTF-8 байтов инструкции и задачи
ограничена `2048 - max_tokens - 160` (1504 при 384). Это консервативная граница
для byte-level tokenizer, а не замер токенов: часть длинных задач пропускается
как `context_too_large`. Контекст и параметры llama.cpp не увеличивались.

## Секреты и журнал

Все пути ниже на Pi, вне исходников и Git:

- `~/.config/stepik-daily-bot/llm.key` — отдельный ключ LLM, права `600`, каталог `700`.
- `~/.config/stepik-daily-bot/stepik.env` — OAuth Client ID/secret и ожидаемый user ID, `600`.
- `~/.local/state/stepik-daily-bot/progress.json` — приватный журнал с ответами,
  попытками и подтверждениями. Сохранять при обновлениях.
- `~/.local/state/stepik-daily-bot/reports/` — отчёты без токенов, условий и ответов.
- `~/.local/state/stepik-daily-bot/benchmark.json` — синтетический замер.
- `~/.local/state/stepik-daily-bot/gateway-check.json` — авторизация/SSE/429.

Отчёты включают названия курсов и ID аккаунта/шагов, поэтому тоже приватные.
Не публиковать полный state. Не включать HTTP debug, `set -x`, печать env/ключей.
OAuth access token живёт только в памяти. Секреты не передаются в argv.
`.env.example` — шаблон; автоматически не читается. Файл конфигурации не
исполняется shell, `source` не требуется. Права шире `600` запрещены.

Ключ `stepik` создан через существующий `raspberry-llm/access.py`.
Отзыв только ключа бота:

```bash
python3 ~/projects/raspberry-llm/access.py revoke-key --name stepik
```

Для ротации создать новый ключ с этим именем после отзыва и безопасно перенести
его в `llm.key` на самом Pi из приватного credential storage, без вывода значения.
Личный ключ и пароль чата менять не требуется.

## Ввод OAuth: действие владельца

В своём браузере войти в Stepik и создать приложение на
[странице OAuth](https://stepik.org/oauth2/applications/): Client type
**Confidential**, grant type **Client credentials**, под нужным аккаунтом.
Пароль Stepik не нужен. Грант и `read write` документированы в
[официальном API](https://github.com/StepicOrg/Stepik-API#oauth-2).

В обычном собственном терминале, не в терминале агента с записью ввода:

```bash
ssh -t raspberry 'python3 /home/admin/projects/stepik-daily-bot/configure.py'
```

Client ID и secret вводятся скрыто. Числовой user ID взять из URL своего профиля.
Скрипт создаёт приватный `stepik.env`, существующий файл не затирает.
Ключи в чат не присылать. Последующие изменения — локальным редактором на Pi.

## Порядок проверки аккаунта

Далее команды на Pi:

```bash
cd ~/projects/stepik-daily-bot
.venv/bin/python bot.py --check-account
.venv/bin/python bot.py --dry-run --max-candidates 10000 --max-steps 10000
python3 -m json.tool ~/.local/state/stepik-daily-bot/reports/latest-dry-run.json
```

Чтение не создаёт attempts/submissions и не вызывает модель. POST нужен только
для OAuth-обмена, к ресурсам идут GET. ID должен совпасть с ожидаемым в конфигурации.

Для большого аккаунта использовать `--max-candidates 100000 --max-steps 100000`.
Реальный API проверен: lessons, steps, progresses и attempts поддерживают
пакетный GET по `ids[]`. Уроки и прогресс читаются пакетами внутри раздела.
Полная собственная история correct читается один раз на аудит с пагинацией;
владельцы и step ID сверяются через соответствующие attempts. Несовпадение
владельца/схемы останавливает аудит. Реальный `status=correct` возвращает также
legacy `settled`: статус проверяется локально; неизвестные/pending шаги
исключаются с причиной `prior_unknown_or_pending_verdict`, не засчитываются
как correct. Wrong/partially_correct не превращаются в прежние полные решения.
В пишущих запусках индекс не используется:
нужен новый клиент и свежие GET перед отправкой. Ход обхода виден в
`reports/inventory-progress.json`. Прерванный аудит помечается incomplete,
не открывает режим отправки и не выдаётся за полный запас задач.

В отчёте: `course_list`, `per_course.types/reasons/candidates`, `api_samples`,
`inventory_complete`, `traversal_skips`, `stop_reason`. Кандидат имеет явный
`progress=false` и не имеет прежних correct в полной истории. `candidates // 26`
— верхняя граница дней только при 100% успехе и пригодности свежих dataset.
При неполном обходе весь запас неизвестен. Ошибка OAuth не означает ноль задач.

`api_samples` читает существующие attempts/submissions максимум у 20 шагов
(до трёх образцов каждого поддержанного типа, включая уже решённые):
сохраняются типы полей, форма dataset/reply и известный статус без значений ответа.
Пустая история не подтверждает формат свежей попытки: он проверяется в пробе.
Форматы сверены с официальными
[SubmissionUtility](https://github.com/StepicOrg/SubmissionUtility/blob/master/submitter.py)
и [Android-моделями](https://github.com/StepicOrg/stepik-android/tree/master/model/src/main/java/org/stepik/android/model).
Это публичные контракты, не захват API вашего аккаунта.

После изучения полного отчёта запаса — одна проба:

```bash
.venv/bin/python bot.py --canary
.venv/bin/python bot.py --report
```

Максимум один POST ответа за вызов, даже если ответ wrong. Прогресс, история и
граница UTC перепроверяются после модели и непосредственно перед POST.
Успешная canary той же модели повторно не отправляется. Открыть
`https://stepik.org/step/STEP_ID`, сверить полное принятие и submission ID из state.
Затем зафиксировать свою визуальную проверку и провести малую серию:

```bash
.venv/bin/python bot.py --approve-canary
.venv/bin/python bot.py --trial
.venv/bin/python bot.py --report
```

`--trial` требует успешную canary и допускает до трёх POST за запуск.
Для ежедневного режима нужны три разных полностью принятых новых шага в trial,
та же модель/аккаунт и ручная проверка canary. Wrong, pending и skip не открывают
этот режим. Повторные осознанные запуски trial сохраняют дневные лимиты.
Правильные пробные решения входят в дневные 26, не идут сверх цели.

## Засчитывание и восстановление

Только новый уникальный шаг, своя посылка/попытка, `correct`, `score=1`, passed
progress и непротиворечивое серверное время с TZ. Wrong, partially_correct,
correct с неполным score, прежние решения и pending не засчитываются.
День — UTC-дата серверной посылки, а не запуска процесса.

Поддержаны choice, number, string, sorting, matching, math, Python 3 code при
проверенном dataset. Число строкой, выбор boolean-массивом нужной длины и
кардинальности, перестановки с нуля, Python language точно из шаблона.
Код на Pi не выполняется; ast проверяет только синтаксис, правильность — Stepik.
Экзамены, review, visual/внешние материалы, неизвестные типы, недоступные разделы
и шаги с ограничениями отправок пропускаются с указанной причиной.

`flock` исключает два экземпляра. Атомарная запись + fsync сохраняют журнал перед
POST. Потерянный ответ на POST не повторяется: `sending` блокирует дальнейшие
отправки до сверки через GET, с поддержкой прямого и wrapped reply.
Пустой ответ API после timeout не доказывает, что поздняя запись не появится.

```bash
.venv/bin/python bot.py --reconcile
.venv/bin/python bot.py --report
```

Не удалять state для снятия неоднозначности. Состояние другого аккаунта и
повреждённый JSON останавливают работу. Лимиты по умолчанию: 104 кандидата/попытки
в UTC-день, один шаг не более раза за день, до 104 POST за полный запуск, цель 26
подтверждений. Canary/trial имеют более строгие лимиты. Другой клиент или ручное
решение того же шага одновременно создают API-гонку: во время пробы так не делать.

Коды выхода: `0` — завершён режим/достигнута цель, `2` — недобор/неудачная проба,
`3` — неразрешённая отправка или блокировка Stepik, `1` — ошибка, `130` — остановка.
Отчёт: actual accepted, shortfall, причины, время на задачу, LLM usage/timings,
ID принятых шагов и неразрешённые посылки. `--report` пересчитывает счётчик
текущего UTC-дня: вчерашние 26 не выдаются за сегодняшний результат.

## systemd и эксплуатация

`.venv` создан через `python3 -m venv --system-site-packages`; используется
установленный requests. Тяжёлых служб/контейнеров нет, VPN и сайты не менялись.
Установщик без флага устанавливает/проверяет units и оставляет таймер выключенным:

```bash
bash scripts/install-systemd.sh
systemctl is-enabled stepik-daily-bot.timer
systemctl list-timers --all stepik-daily-bot.timer
systemd-analyze calendar '*-*-* 05:00:00 UTC'
systemd-analyze verify /etc/systemd/system/stepik-daily-bot.service /etc/systemd/system/stepik-daily-bot.timer
```

После всех живых проверок включить:

```bash
bash scripts/install-systemd.sh --enable
```

Установщик и `--submit` проверяют trial/canary. Без OAuth-файла systemd пропускает
запуск. `Persistent=true` догоняет пропущенный запуск после включения/загрузки.
Расписание 05:00 UTC / 08:00 Москвы; максимум 11 часов работы бота, TimeoutStartSec
12 часов. Остановка новых попыток/ответов за 20 минут до 00:00 UTC.
Restart on failure через 15 минут, максимум 3 запуска/час. Обычный недобор (exit 2)
не вызывает restart. Сначала восстановление журнала, потом новые задачи.

```bash
systemctl status stepik-daily-bot.service stepik-daily-bot.timer --no-pager
sudo journalctl -u stepik-daily-bot.service -n 60 --no-pager
systemctl status raspberry-llm raspberry-llm-gateway --no-pager
free -h
vcgencmd measure_temp
vcgencmd get_throttled
sudo systemctl disable --now stepik-daily-bot.timer
sudo systemctl stop stepik-daily-bot.service
```

Остановка может оставить sending: следующий запуск делает reconcile. Полный reboot
Pi не выполнен; перезапуск отдельных LLM-служб не равен проверке загрузки устройства.
Исходный ZIP сохранён. `python3 scripts/package.py` собирает архив по allowlist
без конфигурации, ключей, state, venv и журналов.
