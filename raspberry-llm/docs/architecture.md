# Архитектура собственной LLM-службы

## Что именно принадлежит вам

Текущая установка — готовая модель с открытыми весами на вашем оборудовании.
Вы управляете весами, API, инструкциями, данными, журналированием и доступом.
Запрос обрабатывается на Raspberry Pi; для работы уже скачанных весов внешний
провайдер генерации не нужен. Это не обучение новой модели с нуля.

Три уровня адаптации:

1. Системная инструкция, примеры и JSON Schema: формат и правила ответа.
2. RAG: поиск в ваших документах и передача найденных фрагментов в контекст.
3. Дообучение LoRA/QLoRA: изменение поведения на подготовленных примерах.

Начинать разумно с первого уровня и проверяемого набора задач. Для внутренних
знаний добавлять RAG. Дообучение оправдано, когда инструкции и примеры не дают
стабильного поведения. Обучение с нуля требует большого корпуса, подготовки
токенизатора, многих циклов обучения и вычислительного бюджета вне этого Pi.

## Как работает выбранная Qwen3-4B-Instruct-2507

Это плотная авторегрессионная decoder-only Transformer-модель: для каждого
следующего токена используются её слои. Это не MoE-модель с выбором экспертов.

Путь вычислений: текст → токенизатор → векторы токенов → 36 Transformer-блоков
→ распределение вероятностей следующего токена → выбор токена → повтор.

Параметры из официальной конфигурации:

| Параметр | Значение |
|---|---|
| Объём | около 4 млрд параметров |
| Блоки | 36 |
| Hidden size | 2560 |
| Attention heads / KV heads | 32 / 8 |
| Размерность головы | 128 |
| Intermediate size | 9728 |
| Словарь | 151936 токенов |
| Исходный предел контекста | 262144 токена |
| Контекст этой установки | 2048 токенов |

GQA использует меньше наборов ключей и значений, чем голов внимания, уменьшая
KV-кэш. RoPE кодирует положение токенов; RMSNorm нормализует активации;
SwiGLU используется в полносвязной части блока. KV-кэш хранит промежуточные
ключи и значения уже обработанных токенов и ускоряет продолжение генерации.

Исходные веса представлены с плавающей точкой. GGUF — формат хранения весов,
метаданных и токенизатора для llama.cpp. Q4_K_M — смешанная блочная
квантизация преимущественно до 4 бит: она уменьшает память и трафик памяти
ценой некоторой потери качества. Не все тензоры занимают ровно 4 бита.

## Почему размер файла не равен потреблению RAM

Память расходуется на веса, KV-кэш, рабочие буферы вычислений и сервер.
Файловый кэш ОС и mmap усложняют сравнение RSS с общей занятой памятью.
Для текущей модели KV-кэш в FP16 при 2048 токенах оценивается так:

`2 × 36 × 8 × 128 × 2048 × 2 байта = 288 МиБ`.

Это только кэш, без весов и рабочих буферов. Удвоение контекста примерно
удваивает размер такого кэша. Несколько параллельных контекстов также увеличивают
память. Поэтому исходное большое окно модели не используется целиком.

Для предварительной оценки весов: `число параметров × битность / 8`.
Для 8B и 4 бит это около 4 ГБ до накладных расходов. До остановки skin-cancer-ai
доступно было лишь около 3,4 ГиБ RAM; после остановки доступно около 5,8 ГиБ
при уже загруженной маленькой модели. Поэтому 4B стала разумным кандидатом.
8B потребует дополнительной проверки запаса памяти и будет медленнее на CPU.
Любую большую модель сначала проверять при реальной нагрузке. Свободный диск
или swap не заменяют RAM. Repack держит дополнительное представление весов
в памяти и ускоряет CPU. После остановки сайта можно проверить этот обмен
памяти на скорость; экономный режим `LLM_REPACK=0` отключает repack.

## Архитектура приложений

Минимальный путь:

`приложение → серверная часть приложения → локальный LLM API → модель`.

Для удалённого проекта API доступен через SSH-туннель. Если появятся несколько
потребителей, перед моделью нужен небольшой API-шлюз: аутентификация проектов,
лимиты длины входа/ответа, ограниченная очередь, таймауты и отмена запросов.
Текущий сервер имеет один слот генерации; ожидание других запросов не означает
одновременную генерацию. Сам слот не устанавливает ограниченную очередь.
Настройка `--n-predict` задаёт значение по умолчанию и не заменяет лимиты шлюза.

Для RAG путь расширяется:

`документы → разбиение на фрагменты → поисковый индекс`;
`вопрос → поиск → несколько фрагментов с ID → промпт → модель → ответ с ID`.

Начальный вариант на этом Pi — полнотекстовый поиск в SQLite FTS5 или уже
имеющейся БД. Для качественного поиска по русскому тексту отдельно проверить
морфологию и словарь запросов. Если нужен семантический поиск, индексирование
эмбеддингов можно выполнять на рабочем компьютере, а Pi передавать готовый
индекс. Не загружать вторую embedding-модель одновременно без замеров RAM.

RAG не меняет веса. Модель может ошибаться даже при правильных фрагментах:
приложение проверяет ссылки и допускает ответ «недостаточно данных».

## Подходящие задачи

- Извлечение полей в JSON из короткого текста с последующей валидацией.
- Классификация обращений по небольшому набору категорий.
- Короткие резюме и переформулирование.
- Ответы по нескольким коротким найденным фрагментам.
- Локальные прототипы ассистентов и фоновые задачи с небольшой очередью.

Сложное программирование, длинные документы, устойчивое многошаговое
планирование и много одновременных пользователей потребуют другой мощности
и проверки более крупных моделей. Эта текстовая модель не принимает изображения
и аудио. Поддержка tool calling сервером сама по себе не обеспечивает качество
выбора инструментов маленькой моделью. Выполняет инструмент сервер приложения.

## Дообучение

Готовить пары вход/ожидаемый ответ с проверенными примерами вашего сценария.
Разделить train, validation и test, исключив почти одинаковые примеры между ними.
Сначала зафиксировать качество базовой модели на том же test-наборе.

LoRA обучает небольшие добавочные матрицы; QLoRA уменьшает требования к памяти
при обучении базовых весов в квантизованном виде. Практический путь — обучение
на отдельной GPU-машине, проверка адаптера, объединение с исходной моделью,
экспорт в GGUF, квантизация и повторная оценка на Pi. Совместимость экспортера
и версии llama.cpp проверять для конкретной архитектуры. Обновление весов
меняет качество, поэтому успешного старта процесса недостаточно.

## Оценка и эксплуатация

Собрать хотя бы 50–100 реальных обезличенных примеров каждого важного сценария.
Измерять отдельно правильность содержания, валидность JSON и бизнес-правила,
долю отказов, задержку первого токена, полное время, токены/с, RAM и температуру.
Проверить короткий и длинный вход, холодный старт и очередь из нескольких
запросов. Три запроса probe.py проверяют подключение, но не заменяют эту оценку.

Streaming улучшает ощущение ожидания, но не сокращает сам объём вычислений.
История диалога хранится приложением и передаётся повторно; её нужно ограничивать.
Изменение промпта, модели, квантования или контекста считать изменением версии
с повторной оценкой. Хранить исходный URL, revision, SHA256, параметры запуска
и результаты. При росте нагрузки сохранить контракт API и перенести инференс
на более мощный узел; Pi может остаться шлюзом и владельцем RAG-данных.
