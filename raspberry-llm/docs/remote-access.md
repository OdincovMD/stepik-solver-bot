# Личный чат и внешний API

## Адреса

- Чат: **https://skin-cancer-ai.ru/llm/**.
- Вход, управление текущим входом и выход: https://skin-cancer-ai.ru/llm/login.
- API base URL: **https://skin-cancer-ai.ru/v1**.
- Модель в запросах: `raspberry-llm`.

Используется существующий домен и существующий `tuna-http-100.service` от
остановленного сайта skin-cancer-ai. Новый туннель и новые DNS-записи не нужны.
Контейнеры старого сайта остаются остановленными; данные и тома сохранены.
Туннель дашборда `tuna-http-8080.service`, SSH-туннели Tuna и VPN не изменялись.

## Схема

`телефон/компьютер → HTTPS Tuna → существующий туннель → 127.0.0.1:18085
→ gateway.py → 127.0.0.1:11434 → существующий llama.cpp`.

TLS завершается на инфраструктуре Tuna. Браузер и клиент проверяют публичный
сертификат. Шлюз и модель не слушают публичные интерфейсы Pi. Инспектор Tuna
отключён (`--inspect=false`), журналирование запросов шлюза отключено.
Пароли, ключи, cookies и тексты запросов не выводятся в журналы.

Встроенный UI llama.cpp работает в имеющейся сборке; он отдаёт gzip и требует
поддержку gzip клиентом. HTML/JS исполняется браузером. Отдельный Node/Open WebUI
или база чатов на Pi не устанавливались. История интерфейса хранится в браузере
на устройстве; между телефоном и компьютером автоматически не синхронизируется.
Дополнительный шлюз занимает около 25 МиБ RSS. Ограничение его виртуального
адресного пространства — 512 МиБ; malloc-арены ограничены двумя, чтобы кэш
потоков не упирался в адресный лимит. Это не лимит RSS модели.
Playwright и OpenAI SDK использовались для QA на рабочем компьютере, а не как
новые зависимости сервисов Pi.
После перезагрузки страницы активная генерация не восстанавливается в фоне.
Браузерные инструменты UI по умолчанию отключены: для обычного чата они
расходуют небольшой контекст и увеличивают время первого ответа. Использована
штатная настройка именно UI b12359, без изменения бинарника или модели.
Существующие настройки браузера не перезаписываются; владелец может изменить
их через интерфейс. При обновлении llama.cpp этот ключ нужно проверить заново.

## Доступ

Учётные данные находятся только на Pi:

- `~/.config/raspberry-llm/access.json`: солёный PBKDF2-хеш пароля, хеши API-ключей,
  секрет сессий, HTTPS Origin; права 0600.
- `~/.config/raspberry-llm/credentials.json`: исходный сгенерированный пароль и
  исходные API-ключи для владельца; права 0600, каталог 0700. Не помещать в Git.

Логин по умолчанию: `owner`. Узнать первоначальный пароль можно самостоятельно
по SSH, прочитав credentials.json в своём терминале. Не отправляйте файл в чат.
Удобнее сразу задать свой пароль с маскированным вводом:

```bash
ssh -t raspberry 'python3 /home/admin/projects/raspberry-llm/access.py set-password'
```

Изменение пароля отзывает все веб-сессии, не меняя API-ключи. Веб-сессия действует
12 часов, cookie имеет Secure, HttpOnly, SameSite=Strict. Перезапуск шлюза также
отзывает веб-сессии; после него нужно войти заново. API-ключи переживают рестарты.
Выход из текущей веб-сессии доступен по странице `/llm/login` и отзывает cookie
на сервере. Авторизация дашборда через PAM остаётся отдельной.

Для клиента, например Stepik, создать отдельный именованный ключ:

```bash
ssh raspberry 'python3 /home/admin/projects/raspberry-llm/access.py add-key --name stepik'
ssh raspberry 'python3 /home/admin/projects/raspberry-llm/access.py revoke-key --name stepik'
```

Команды не печатают ключи. Прочитайте нужный ключ из приватного credentials.json
в своём терминале и передайте его будущему приложению через secret/env-файл.
Отзыв действует со следующего запроса без рестарта служб. Существующий ключ
`personal` можно использовать для личных клиентов. API принимает
`Authorization: Bearer <ключ>`; пароль веб-чата не является API-ключом.

## API и ограничения

Сохраняются `GET /v1/models` и `POST /v1/chat/completions`. Принимаются текстовые
сообщения строкой или OpenAI-частями `[{type:"text",text:"..."}]`, streaming,
JSON response_format и определения функций. Выполнение серверных инструментов,
доступ к файлам/оболочке, метрикам и управляющим эндпоинтам не публикуются.
Изображения и аудио не поддерживаются выбранной текстовой моделью.

Пример будущего Python-клиента с уже установленным OpenAI SDK:

```python
import os
from openai import OpenAI

client = OpenAI(
    base_url="https://skin-cancer-ai.ru/v1",
    api_key=os.environ["LLM_API_KEY"],
    timeout=650,
    max_retries=0,
)
stream = client.chat.completions.create(
    model="raspberry-llm",
    messages=[{"role": "user", "content": "Коротко объясни, что такое API."}],
    max_tokens=128,
    stream=True,
)
for event in stream:
    if event.choices:
        print(event.choices[0].delta.content or "", end="", flush=True)
```

Ограничения шлюза:

- Один активный запрос генерации. Второй получает **429** и `Retry-After: 10`,
  без очереди; клиент сам предлагает повтор или делает ограниченный backoff.
- Контекст модели прежний: **2048** токенов, включая историю и ответ.
- Ответ: по умолчанию 256, допустимо **1–512** токенов. UI-значение `-1`
  преобразуется в безопасное значение по умолчанию 256.
- JSON-запрос до 128 КиБ, до 100 сообщений; это не замена токенному контексту.
- Шлюз отводит запросу до 600 секунд; клиенту задано 650 секунд. SSE-комментарии
  keepalive идут каждые пять секунд во время ожидания; streaming не буферизуется.
  Проверен реальный запрос около 110 секунд, а не весь возможный предел 600.
- Параметры существующего llama.cpp, включая `--timeout 180`, не менялись.
- Закрытие streaming-соединения отменяет upstream-запрос. Прямой доступ
  локальных приложений к 11434 обходит ограничитель шлюза: используйте 18085
  с ключом или публичный API, чтобы все приложения делили один ограничитель.

После Stop CPU может дозавершить текущий batch. В реальной проверке после
разрыва соединения следующий короткий запрос завершился через 10,26 секунды.
В UI по умолчанию отключены необязательные инструменты; их отсутствие и
неподдерживаемое восстановление фоновых стримов могут давать ожидаемые 404
для `/tools`, `/build.json` и `/v1/streams/lookup`. Это не ошибки генерации.

Основные ошибки: 401 — нет/неверна авторизация; 403 — неподходящий Origin для
веб-сессии; 400 — неподдерживаемый запрос/слишком большой контекст; 429 — модель
занята; 503 — модель временно недоступна. Не повторять запросы бесконечно.

## Управление и диагностика

```bash
ssh raspberry 'systemctl status raspberry-llm raspberry-llm-gateway tuna-http-100 --no-pager'
ssh raspberry 'systemctl is-enabled raspberry-llm raspberry-llm-gateway tuna-http-100'
ssh raspberry 'sudo journalctl -u raspberry-llm-gateway -u tuna-http-100 -n 40 --no-pager'
ssh raspberry 'ss -lnt | grep -E "11434|18085"'
ssh raspberry 'free -h; vcgencmd measure_temp; vcgencmd get_throttled'
curl -I https://skin-cancer-ai.ru/llm/login
curl -i https://skin-cancer-ai.ru/v1/models
```

Последний запрос без ключа должен вернуть 401. Не передавайте реальные ключи
в командной строке curl: используйте защищённый файл заголовков или приложение,
читающее ключ из env/secret-файла. Не включайте verbose-трассировку с ключами.

Перезапуск только внешнего шлюза и существующего туннеля:

```bash
ssh raspberry 'sudo systemctl restart raspberry-llm-gateway tuna-http-100'
```

Модель перезапускать отдельно, когда нет активного запроса. После рестарта ей
нужно время загрузить веса. Веб-сессия после рестарта шлюза потребует нового входа.

Проверен перезапуск всех трёх служб: модель стала готова через 12 секунд,
затем внешний API успешно проверен настоящим OpenAI SDK 3.57.0, включая SSE.
Все три службы active/enabled. Сам Pi не перезагружался: проверка касается
рестарта служб и их boot-зависимостей, а не фактического полного reboot хоста.
Это сохраняет текущие SSH/VPN-соединения пользователей во время проверки.

Файлы установки:

- Исходники: `/home/admin/projects/raspberry-llm`.
- Шлюз: `/etc/systemd/system/raspberry-llm-gateway.service`.
- Drop-in существующего туннеля:
  `/etc/systemd/system/tuna-http-100.service.d/50-raspberry-llm.conf`.
- Прежняя конфигурация сохранена в приватном
  `~/.local/share/raspberry-llm/backups/tuna-http-100-*.service`.

Для немедленного закрытия внешнего доступа остановить `tuna-http-100.service`.
Для отката к старому адресу порта 100 перенести собственный drop-in из каталога
`.service.d`, выполнить daemon-reload и перезапустить этот туннель. Старый сайт
от этого не запускается. Не направлять туннель непосредственно на порт 11434.

## Выбор маршрута и границы проверки

Доступный VPN-конфиг Pi прочитан без вывода ключей; VPN использует VLESS/REALITY
на 443. SSH-доступ к предполагаемому текущему VPS на 22 не получен. У нескольких
старых адресов SSH изменились ключи; их не принимали и не заменяли. Серверную
конфигурацию Xray без SSH проверить не удалось, поэтому VPS не менялся.

Владелец предпочёл существующий Tuna. HTTPS-домен skin-cancer-ai.ru уже работал,
а соответствующий сайт был остановлен владельцем ранее. Его туннель переиспользован.
У api.pi-hardbox.ru отдельно наблюдался обрыв TLS; его маршрут не менялся.
Для выбранного решения доступ к VPS и изменения DNS не требуются.

Результаты реальных проверок: `../results/external-*.json`,
`../results/browser/`, `../results/latency-baseline.json`.
Сравнимые замеры и ограничения: [измерения](measurements.md).
